# Cost Management Notes

## 1. 目的

この文書では、Azure環境におけるコスト管理の初期方針を整理する。

初期版では、詳細なFinOps設計までは扱わない。まずは、リソースの所有者、用途、環境、コスト集計単位が分かる状態を作ることを目的とする。

コスト管理は、請求金額を確認するだけではない。どのリソースが、何の目的で、誰の管理で、どの費用単位に紐づいているかを追えることが重要である。

## 2. 基本方針

コスト管理では、以下を基本方針とする。

| 項目 | 方針 |
|---|---|
| 集計単位 | Resource GroupとTagを組み合わせる |
| 必須タグ | CostCenter / Environment / Workloadを重視する |
| 検証環境 | 低コストで作成し、不要時は削除する |
| Evidence | デプロイ後のリソースと削除結果を残す |
| 運用 | 不要リソースの棚卸しを前提にする |

初期版では、複雑な予算管理やチャージバックまでは行わない。

## 3. コスト管理で使う情報

コスト管理に使う主な情報は以下。

| 情報 | 用途 |
|---|---|
| Resource Group | 大まかな用途・ライフサイクル単位 |
| Environmentタグ | dev / test / prodなどの環境別集計 |
| CostCenterタグ | 部門・プロジェクト別集計 |
| Workloadタグ | システム・用途別集計 |
| Ownerタグ | 問い合わせ先、責任主体 |
| ManagedByタグ | IaC管理か手動管理かの確認 |

タグが未設定の場合、Cost Management上で集計しづらくなる。そのため、タグ標準とCost管理はセットで扱う。

## 4. Resource Group設計との関係

Resource Groupは、コスト確認の単位としても使う。

初期版では、以下のように用途を分ける。

| Resource Group | 用途 |
|---|---|
| rg-platform-monitoring | Log Analyticsなど共通監視基盤 |
| rg-platform-network | 最小ネットワーク構成 |
| rg-workload-sample | 検証用ワークロード |
| rg-sandbox-* | 一時検証用 |

共通基盤とワークロードを同じResource Groupに混ぜると、コストや権限の整理が難しくなる。そのため、用途やライフサイクルが近い単位で分ける。

## 5. 低コスト検証の方針

このリポジトリの初期実装は、個人検証環境でも扱えるように低コストを前提とする。

考慮する点は以下。

- 高額になりやすいSKUを避ける
- 常時稼働が必要なリソースを増やしすぎない
- 検証後に削除できる構成にする
- ログ収集量を増やしすぎない
- 不要なPublic IPやVMを作成しない
- Teardown手順を用意する

特にLog Analyticsは、収集量が増えるとコストに影響する。初期段階では、必要なログに絞る。

## 6. 予算とアラート

初期版では、詳細な予算アラート設計は対象外とする。

ただし、実運用では以下を検討する。

- Subscription単位の予算
- Resource Group単位の予算
- CostCenter単位の予算
- 月次のしきい値アラート
- 急激なコスト増加の検知

予算アラートは、通知先や対応フローとセットで意味を持つ。通知だけ設定しても、誰が確認し、どう対応するかが決まっていなければ運用されない。

## 7. タグ未設定時の影響

タグ未設定のリソースが増えると、以下の問題が起きる。

- コストの持ち主が分からない
- 不要リソースを削除してよいか判断しづらい
- 棚卸し時に確認が必要になる
- 環境別、用途別の集計ができない
- 問い合わせ先が分からない

そのため、CostCenter、Environment、Workload、Ownerは初期段階から付与する。

## 8. Azure CLI確認方針

リソース一覧とタグ確認。

~~~bash
az resource list \
  --query "[].{name:name,type:type,resourceGroup:resourceGroup,tags:tags}" \
  --output table
~~~

Resource Groupのタグ確認。

~~~bash
az group list \
  --query "[].{name:name,location:location,tags:tags}" \
  --output table
~~~

利用量やコストの詳細確認は、環境や権限により利用できるコマンドが異なるため、初期版ではEvidenceとしてタグとリソース構成を中心に残す。

## 9. Teardown方針

検証環境では、作成後に削除できることを前提にする。

削除時には、以下を確認する。

- 対象Resource Groupが正しいか
- 本番や共有環境を含んでいないか
- 削除対象に想定外リソースがないか
- BackupやLockが残っていないか
- 削除後に残存リソースがないか

Teardownは、単に削除コマンドを実行する作業ではない。削除前確認と削除後確認まで含めてRunbook化する。

## 10. 運用時の確認観点

コスト管理では、以下を確認する。

- CostCenterタグが付与されているか
- Environmentごとに集計できるか
- Workloadごとにリソースを追えるか
- 不要な検証リソースが残っていないか
- Log Analyticsの収集量が過剰でないか
- Public IPやVMなど、意図しないコスト要因がないか
- 削除手順とEvidenceが残っているか

## 11. まとめ

初期版のCost管理では、複雑なFinOps運用よりも、まず集計できる状態を作ることを重視する。

Resource Group設計とタグ標準を組み合わせ、誰の、何の、どの環境のリソースかを追えるようにする。検証後に削除できることも、コスト管理の一部として扱う。
