# Exception Operation

## 1. 目的

この文書では、Azure Governance Baselineにおける例外運用を整理します。

Policy、RBAC、Tag、Logなどの標準を決めても、実運用では例外が発生します。問題は、例外が発生することではなく、理由や期限がないまま通常運用へ混ざることです。

## 2. 基本方針

| 項目 | 方針 |
|---|---|
| 例外の扱い | 標準からの一時的な逸脱として扱う |
| 記録 | 理由、影響、期限、承認者を残す |
| 期限 | 原則として期限を設定する |
| 見直し | 定期的に継続要否を確認する |
| 恒久化 | 恒久化する場合は標準側を見直す |
| Evidence | 例外適用と見直し結果を残す |

例外は、作業を止めるための仕組みではありません。標準と現実の差分を管理するための仕組みです。

## 3. 例外が発生しやすい領域

| 領域 | 例 |
|---|---|
| Policy | 特定リソースだけDeny対象から外す |
| Tag | CostCenterが未確定の一時リソース |
| Location | サービス都合で許可外リージョンを使う |
| Public IP | 一時的な検証でPublic IPが必要 |
| Diagnostic Settings | 対応していないリソース、またはコスト都合で未設定 |
| RBAC | 一時的にContributor以上が必要 |
| Resource Lock | 削除検証のため一時的にLockを外す |

## 4. 例外記録項目

例外を認める場合は、最低限以下を記録します。

| 項目 | 内容 |
|---|---|
| 例外ID | 管理用の番号 |
| 対象 | Subscription、Resource Group、Resourceなど |
| 標準との差分 | どのルールから外れるのか |
| 理由 | なぜ例外が必要か |
| 影響範囲 | セキュリティ、コスト、運用への影響 |
| 代替策 | 標準に合わせる方法がないか |
| 承認者 | 誰が認めたか |
| 期限 | いつまで例外とするか |
| 見直し予定 | 再確認する日付 |
| 終了条件 | 何をもって例外終了とするか |

## 5. 記録例

| 項目 | 記入例 |
|---|---|
| 例外ID | EX-2026-001 |
| 対象 | `rg-apg-dev-workload-sample` |
| 標準との差分 | Public IP利用を一時的に許可 |
| 理由 | 外部接続検証のため一時的に必要 |
| 影響範囲 | インターネット公開経路が発生する |
| 代替策 | Private接続は検証環境では未準備 |
| 承認者 | platform-owner |
| 期限 | 2026-06-30 |
| 見直し予定 | 2026-06-15 |
| 終了条件 | 検証完了後にPublic IPを削除 |

## 6. ライフサイクル

例外は、以下の流れで扱います。

1. 例外の必要性を確認する
2. 標準に合わせる代替案がないか確認する
3. 影響範囲を整理する
4. 承認者を決める
5. 期限を決める
6. 例外を適用する
7. Evidenceを残す
8. 期限前に見直す
9. 不要になったら解除する

長期間続く例外は、例外ではなく標準側を見直すべき可能性があります。

## 7. Policy例外

Policy例外では、適用除外やスコープ分離を検討します。

確認観点は以下です。

- Exemption対象が広すぎないか
- 期限が設定されているか
- 理由が具体的か
- 承認者が明確か
- Exemptionが放置されていないか

## 8. RBAC例外

一時的に強い権限が必要になる場合でも、恒久権限として放置しません。

確認観点は以下です。

- なぜそのロールが必要か
- ContributorではなくOwnerが必要な理由があるか
- Resource Group単位で足りないか
- 期限後に削除する運用があるか
- 付与結果と削除結果を残しているか

## 9. Tag例外

Tagは運用上重要ですが、作成時点で値が確定しない場合があります。

その場合は、仮値を入れるか、例外として期限を残します。空欄や未設定のまま放置する状態は避けます。

## 10. Evidence

例外運用では、以下をEvidenceとして残します。

- 例外申請内容
- 承認結果
- 適用内容
- 期限
- 見直し結果
- 解除結果

Evidenceは、監査のためだけではなく、後から運用担当者が状況を理解するためにも必要です。

## 11. 運用時の確認観点

- 期限切れの例外が残っていないか
- 理由が曖昧な例外がないか
- 同じ理由の例外が繰り返されていないか
- 例外対象が広すぎないか
- 承認者が明確か
- 解除条件が決まっているか
- 標準側を見直すべき例外がないか

## 12. まとめ

例外は、標準を壊すためのものではありません。

標準と現実の差分を管理するために、理由、影響、承認者、期限、見直し予定を残します。
