# AVD Troubleshooting Flow

## 1. 目的

この文書では、Azure Virtual Desktop接続不可時の初期切り分け観点を整理します。

AVDの接続不可は、AVD基盤、SessionHost / OS、ID、ネットワーク、ユーザー端末など複数の要因で発生します。原因を決め打ちせず、確認済み範囲と未確認範囲を分けることを重視します。

## 2. 基本方針

| 方針 | 内容 |
|---|---|
| 事象を分解する | AVD接続前、接続中、OSログオン後のどこで失敗しているかを分ける |
| 事実を優先する | エラー内容、時刻、対象ユーザー、対象HostPoolを確認する |
| 確認範囲を明確にする | 運用側で見られる範囲と顧客側確認を分ける |
| 原因を決め打ちしない | AVD基盤、ID、OS、ネットワーク、端末を順に確認する |
| 証跡を残す | 確認結果、確認不可範囲、依頼事項を残す |

## 3. 最初に確認する情報

| 項目 | 内容 |
|---|---|
| 発生日時 | いつ発生したか |
| 対象ユーザー | UPNまたはユーザー識別情報 |
| 対象HostPool | どのHostPoolか |
| 対象SessionHost | 分かる場合は対象ホスト |
| エラー内容 | 画面エラー、エラーコード、メッセージ |
| 発生範囲 | 単一ユーザーか、複数ユーザーか |
| 再現性 | 常時発生か、一時的か |
| 接続元 | 端末、ネットワーク、クライアント種別 |
| 直前変更 | ユーザー、端末、ネットワーク、AVD側で変更があったか |

情報が不足している場合は、原因調査より先に前提を確認します。

## 4. 切り分けの流れ

```text
問い合わせ受付
  ↓
事象情報の確認
  ↓
発生範囲の確認
  ↓
AVD基盤側の状態確認
  ↓
SessionHost / OS側の確認
  ↓
ID / 権限側の確認
  ↓
ネットワーク側の確認
  ↓
ユーザー端末 / クライアント側の確認
  ↓
確認結果と次アクションの整理
```

## 5. 発生範囲の確認

| 発生範囲 | 見方 |
|---|---|
| 単一ユーザーのみ | ユーザー割当、ID、端末、プロファイルの可能性が高い |
| 複数ユーザー | HostPool、SessionHost、ネットワーク、共通設定の可能性がある |
| 特定SessionHostのみ | OS、VM、Agent、リソース状態の確認を優先する |
| 全HostPool | AVD基盤、ネットワーク、共通認証、広域障害を確認する |

## 6. AVD基盤側の確認

| 確認項目 | 内容 |
|---|---|
| HostPool状態 | 対象HostPoolが存在するか |
| SessionHost登録状態 | SessionHostがHostPoolに登録されているか |
| SessionHost状態 | Available / Unavailableなどの状態 |
| AllowNewSession | 新規接続が許可されているか |
| AssignedUser | Personal Desktopの場合、対象ユーザーが割当済みか |
| DAG権限 | Desktop Application Groupを利用できるか |
| Active / Disconnected session | 既存セッションが残っていないか |

AVD管理面で異常がない場合、OS、ID、ネットワーク、端末側へ確認範囲を広げます。

## 7. SessionHost / OS側の確認

| 確認項目 | 内容 |
|---|---|
| VM PowerState | VMが起動しているか |
| VM Agent | Azure VM Agentが正常か |
| AVD Agent | AVD Agent / Boot Loaderが正常か |
| RDP設定 | OS上でリモート接続が許可されているか |
| OSイベントログ | ログオン失敗、RDP、サービス異常を確認する |
| ディスク容量 | OS動作に影響する不足がないか |
| CPU / Memory | 高負荷でログオンできない状態でないか |

管理者RDPが可能でも、ユーザー接続が成功するとは限りません。管理者RDPは切り分け材料の一つとして扱います。

## 8. ID / 権限側の確認

| 確認項目 | 内容 |
|---|---|
| Entra IDユーザー | ユーザーが存在し、有効か |
| ADアカウント | ハイブリッド構成の場合、AD側の状態 |
| グループ所属 | DAG利用権限に関係するグループ所属 |
| MFA / 条件付きアクセス | 接続をブロックしていないか |
| リスク状態 | サインインリスクやユーザーリスク |
| パスワード状態 | 期限切れ、ロック、変更要求など |

運用側で確認できない項目は、確認不可として依頼元やID管理担当へ確認を依頼します。

## 9. ネットワーク側の確認

| 確認項目 | 内容 |
|---|---|
| NSG | 必要な通信がブロックされていないか |
| UDR | 想定外の経路になっていないか |
| DNS | 名前解決ができているか |
| Firewall / Proxy | 必要な通信が許可されているか |
| Private Endpoint | 利用している場合、名前解決と接続性 |
| 接続元ネットワーク | 特定拠点やVPN利用時のみ発生していないか |

ネットワーク変更後に発生した場合は、優先して確認します。

## 10. ユーザー端末 / クライアント側の確認

| 確認項目 | 内容 |
|---|---|
| クライアント種別 | Windows App、Remote Desktop Client、Web Clientなど |
| クライアントバージョン | 古いバージョンでないか |
| 端末ネットワーク | 社内、在宅、VPNなど |
| 資格情報キャッシュ | 古い資格情報が残っていないか |
| 他端末での再現 | 端末依存か確認する |
| 他ユーザーでの再現 | ユーザー依存か確認する |

端末側の確認は、運用側で直接見られない場合があります。その場合は、依頼元へ確認事項を明確に返します。

## 11. 確認結果の整理

| 項目 | 内容 |
|---|---|
| 確認できたこと | 運用側で確認済みの事実 |
| 確認できなかったこと | 権限や範囲外により未確認の項目 |
| 異常があった箇所 | 具体的な異常内容 |
| 異常がなかった箇所 | 切り分け済み範囲 |
| 次に必要な確認 | 顧客側、ID担当、ネットワーク担当など |
| 暫定対応 | 必要に応じた回避策 |

「問題ありません」だけではなく、どの範囲を確認した結果なのかを明記します。

## 12. 回答の基本形

顧客または依頼元へ返す場合は、以下の順でまとめます。

1. 確認対象
2. 確認結果
3. 判断
4. 追加確認が必要な項目
5. 次の対応

例です。

```text
対象HostPoolおよびSessionHostの状態を確認したところ、AVD管理面では対象SessionHostは使用可能な状態であり、基盤側で明確な異常は確認されませんでした。

一方で、対象ユーザーの認証または権限前提については当方の確認範囲外となるため、Entra ID / AD側の状態をご確認ください。
```

## 13. 関連スクリプト

| Script | 役割 |
|---|---|
| `Export-AvdHostPoolInventory.ps1` | HostPool、SessionHost、AssignedUser、VM、IPの棚卸し |
| `Set-AvdPersonalDesktopAssignment.ps1` | AssignedUserとDAG権限の確認 |
| `Start-AzVmFromCsv.ps1` | VM状態確認と起動 |

トラブルシュートはスクリプトだけでは完結しません。スクリプトは確認材料を集めるための補助として扱います。

## 14. まとめ

AVD接続不可対応では、最初から原因を決め打ちしません。

発生範囲、AVD基盤、SessionHost / OS、ID、ネットワーク、端末の順に確認し、確認済み範囲と未確認範囲を分けて整理します。
