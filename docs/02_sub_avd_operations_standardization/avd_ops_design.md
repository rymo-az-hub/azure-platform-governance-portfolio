# AVD Operations Standard Design

## 1. 目的

この文書では、Azure Virtual Desktop運用で発生しやすい定型作業を、確認、実行、記録まで含めて標準化する考え方を整理する。

本リポジトリの主軸は、Azure Governance / Policy Baselineである。AVD運用標準化は、その考え方を実運用へ落とし込むサブテーマとして扱う。

ここで重視するのは、AVD環境そのものの詳細設計ではない。日々の運用作業で起きやすい確認漏れ、作業者依存、証跡不足、利用者影響を減らすことである。

## 2. 対象とする運用課題

AVD運用では、以下のような課題が発生しやすい。

| 課題 | 内容 |
|---|---|
| 対象確認のばらつき | 作業対象のSessionHost、VM、ユーザー、IP情報の確認粒度が人によって変わる |
| 利用者影響の見落とし | Active sessionの有無や割当状態を確認しないまま作業するリスクがある |
| 作業順序の曖昧さ | SessionHost、VM、NIC、Diskなどの削除順序が整理されていないと削除漏れが起きる |
| 権限前提の不足 | Personal Desktop割当後に、Desktop Application Group側の利用権限が不足する場合がある |
| 証跡不足 | 作業前後の状態やスキップ理由が残らない |
| 手動作業依存 | ポータル操作中心だと、作業者による差が出やすい |

これらは個別作業の問題に見えるが、実際には運用設計の問題である。

## 3. 対象作業

初期版では、以下を対象とする。

| 作業 | 目的 |
|---|---|
| HostPool棚卸し | SessionHost、AssignedUser、VM、NIC、Private IPを確認する |
| SessionHostライフサイクル | 削除や整理時に、利用者影響と削除漏れを抑える |
| Personal Desktop割当 | AssignedUser設定と利用権限の確認を標準化する |
| 接続不可時の切り分け | AVD基盤側、OS側、ID側、ユーザー側の確認観点を整理する |
| 作業チェックリスト | 作業前、作業中、作業後の確認項目を揃える |
| 顧客回答テンプレート | 調査結果や確認依頼を一定の品質で返せるようにする |

## 4. 非対象範囲

以下は初期版では対象外とする。

| 項目 | 理由 |
|---|---|
| AVD全体アーキテクチャ設計 | 本リポジトリの主軸ではないため |
| FSLogix詳細設計 | 別設計領域として扱うため |
| イメージ管理の詳細 | 運用標準化とは切り分けるため |
| Intune / MDM設計 | AVD運用に関係するが範囲が広くなるため |
| ネットワーク詳細設計 | メインテーマのLanding Zone側で扱う余地を残すため |
| 本番運用手順そのもの | 公開可能な一般化資料として扱うため |

実案件固有の手順、顧客名、環境名、社内情報は含めない。

## 5. 共通設計方針

AVD運用標準化では、以下を共通方針とする。

| 方針 | 内容 |
|---|---|
| 入力ファイルで対象を明確にする | 作業対象をCSVやパラメータで明示する |
| 事前確認を必須にする | 対象存在、状態、割当、権限を確認する |
| DryRunを用意する | 変更前に実行予定内容を確認できるようにする |
| 利用者影響を確認する | Active sessionや割当状態を確認する |
| スキップ理由を記録する | 作業しなかった対象の理由を残す |
| 結果をCSVやログで出力する | 作業後に確認できる状態にする |
| 承認フローを代替しない | スクリプトは承認済み作業の補助として扱う |

## 6. スクリプト群の位置づけ

`scripts/avd/` 配下のスクリプトは、運用作業を安全に再現するための補助ツールとして扱う。

想定するスクリプトは以下。

| Script | 用途 |
|---|---|
| `Export-AvdHostPoolInventory.ps1` | HostPool内のSessionHost、AssignedUser、VM、NIC、Private IPを出力する |
| `Remove-AvdSessionHostResources.ps1` | SessionHostと関連Azureリソースの削除を段階化する |
| `Set-AvdPersonalDesktopAssignment.ps1` | Personal DesktopのAssignedUser割当を確認付きで行う |
| `Start-AzVmFromCsv.ps1` | CSV指定のVMを状態確認付きで起動する |

公開用では、実環境の固定値や固有名詞は含めない。サンプル入力ファイルを使い、処理の考え方を示す。

## 7. 利用者影響の回避

AVD運用では、利用者影響を避けるために以下を確認する。

| 確認項目 | 理由 |
|---|---|
| Active session | 利用中ユーザーがいる場合、削除や停止の影響が出る |
| AssignedUser | Personal Desktopで割当済みユーザーを誤って変更しないため |
| Drain mode | 新規接続を制御するため |
| DAG利用権限 | 割当後にユーザーが利用できる状態か確認するため |
| VM状態 | 停止中、起動中、削除済みなどで作業可否が変わるため |
| BackupやLock | 削除や変更がブロックされる可能性があるため |

作業を実行できることと、実行してよいことは分けて考える。

## 8. Evidenceとの関係

AVD運用標準化でも、作業結果をEvidenceとして残す。

Evidenceとして残す対象は以下。

- 作業対象一覧
- 事前確認結果
- DryRun結果
- 実行結果
- スキップ理由
- 作業後確認
- 顧客または関係者への回答内容

証跡は、作業者を責めるためではなく、後から作業内容を追えるようにするために残す。

## 9. 責任分界

スクリプトやRunbookは、運用判断を代替しない。

責任分界は以下のように整理する。

| 領域 | 考え方 |
|---|---|
| 作業対象の承認 | 変更管理または依頼元の責任 |
| 作業手順の実行 | 運用担当者の責任 |
| スクリプトの動作確認 | スクリプト管理者の責任 |
| 実行結果の確認 | 作業者とレビュー者で確認 |
| 例外判断 | 承認者または運用責任者が判断 |
| 顧客影響判断 | 運用責任者または顧客側責任者と合意する |

作業者が、承認、影響判断、技術実行、結果保証をすべて抱えないようにする。

## 10. メインテーマとの関係

AVD運用標準化は、Azure Governance Baselineとは別物ではない。

Governance Baselineで整理した以下の考え方を、実運用へ適用した例として扱う。

- 権限を明確にする
- 対象を明確にする
- 事前確認を行う
- 例外を記録する
- 実行結果をEvidenceとして残す
- 不要リソースを削除できる状態にする
- 作業を属人化させない

そのため、AVD側の資料は単なるスクリプト説明ではなく、CloudOps標準化の具体例として位置づける。

## 11. まとめ

AVD運用標準化では、作業を早く終わらせることだけを目的にしない。

作業対象、前提、影響、実行結果、スキップ理由を明確にし、誰が見ても後から追える状態にする。

これにより、AVD運用で発生しやすい属人化、確認漏れ、証跡不足を減らし、Azure基盤運用全体の品質を上げる。
