# AVD Operations Standard Design

## 1. 目的

この文書では、Azure Virtual Desktop運用で発生しやすい定型作業を、確認、実行、記録まで含めて標準化する考え方を整理します。

AVD運用標準化は、本リポジトリのサブテーマです。Azure Governance / Policy Baselineで整理した考え方を、実運用へ適用した例として扱います。

## 2. 対象とする課題

AVD運用では、以下の課題が発生しやすくなります。

| 課題 | 内容 |
|---|---|
| 対象確認のばらつき | SessionHost、VM、ユーザー、IP情報の確認粒度が作業者により変わる |
| 利用者影響の見落とし | Active sessionやAssignedUserを確認しないまま作業するリスクがある |
| 削除漏れ | SessionHost、VM、NIC、Diskなどの関係が整理されていないとリソースが残る |
| 権限前提の不足 | Personal Desktop割当後にDAG側の利用権限が不足する場合がある |
| 証跡不足 | 作業前後の状態やスキップ理由が残らない |
| 手動作業依存 | ポータル操作中心では、作業者による差が出やすい |

## 3. 対象作業

| 作業 | 目的 |
|---|---|
| HostPool棚卸し | SessionHost、AssignedUser、VM、NIC、Private IPを確認する |
| SessionHostライフサイクル | 削除や整理時に、利用者影響と削除漏れを抑える |
| Personal Desktop割当 | AssignedUser設定とDAG権限確認を標準化する |
| 接続不可時の切り分け | AVD基盤、OS、ID、ネットワーク、端末側に分けて確認する |
| 作業チェックリスト | 作業前、作業中、作業後の確認項目を揃える |
| 顧客回答テンプレート | 確認結果と未確認範囲を分けて回答できるようにする |

## 4. 非対象範囲

| 項目 | 理由 |
|---|---|
| AVD全体アーキテクチャ設計 | 本リポジトリの主軸ではないため |
| FSLogix詳細設計 | ユーザープロファイル設計として別に扱うため |
| イメージ管理 | 運用標準化とは別領域のため |
| Intune / MDM設計 | 範囲が広くなるため |
| 本番運用手順そのもの | 公開可能な一般化資料として扱うため |

実案件固有の手順、顧客名、環境名、社内情報は含めません。

## 5. 共通方針

| 方針 | 内容 |
|---|---|
| 対象を明確にする | CSVやパラメータで対象を指定する |
| 事前確認を行う | 対象存在、状態、割当、権限を確認する |
| DryRunを用意する | 変更前に実行予定内容を確認する |
| 利用者影響を確認する | Active sessionやAssignedUserを確認する |
| スキップ理由を記録する | 作業しなかった対象の理由を残す |
| 結果を出力する | CSVやログで作業後に確認できるようにする |
| 承認を代替しない | スクリプトは承認済み作業の補助として扱う |

## 6. 関連スクリプト

| Script | 用途 |
|---|---|
| `Export-AvdHostPoolInventory.ps1` | HostPool内のSessionHost、AssignedUser、VM、NIC、Private IPを出力する |
| `Remove-AvdSessionHostResources.ps1` | SessionHostと関連Azureリソースの削除を段階化する |
| `Set-AvdPersonalDesktopAssignment.ps1` | Personal DesktopのAssignedUser割当を確認付きで行う |
| `Start-AzVmFromCsv.ps1` | CSV指定のVMを状態確認付きで起動する |

公開用では、実環境の固定値や固有名詞は含めません。サンプル入力ファイルを使い、処理の考え方を示します。

## 7. 利用者影響の確認

AVD運用では、以下を確認します。

| 確認項目 | 理由 |
|---|---|
| Active session | 利用中ユーザーへの影響を避けるため |
| AssignedUser | Personal Desktopの誤変更を避けるため |
| Drain mode | 新規接続を制御するため |
| DAG利用権限 | 割当後にユーザーが利用できる状態か確認するため |
| VM状態 | 停止中、起動中、削除済みなどで作業可否が変わるため |
| Backup / Lock | 削除や変更がブロックされる可能性があるため |

作業を実行できることと、実行してよいことは分けて考えます。

## 8. Evidence

AVD運用標準化でも、作業結果をEvidenceとして残します。

主な記録対象は以下です。

- 作業対象一覧
- 事前確認結果
- DryRun結果
- 実行結果
- スキップ理由
- 作業後確認
- 顧客または関係者への回答内容

## 9. 責任分界

| 領域 | 考え方 |
|---|---|
| 作業対象の承認 | 変更管理または依頼元の責任 |
| 作業手順の実行 | 運用担当者の責任 |
| スクリプトの動作確認 | スクリプト管理者の責任 |
| 実行結果の確認 | 作業者とレビュー者で確認 |
| 例外判断 | 承認者または運用責任者が判断 |
| 顧客影響判断 | 運用責任者または顧客側責任者と合意する |

スクリプトやRunbookは、運用判断を代替しません。

## 10. まとめ

AVD運用標準化では、作業を早く終わらせることだけを目的にしません。

作業対象、前提、影響、実行結果、スキップ理由を明確にし、後から追える状態にすることを重視します。
