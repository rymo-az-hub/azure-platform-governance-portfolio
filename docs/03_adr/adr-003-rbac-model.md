# ADR-003: RBACモデル

## Status

Accepted

## Context

Azure環境では、権限を広く付与すると作業は進めやすくなる一方で、責任範囲や変更影響が分かりにくくなる。

初期段階から権限の考え方を決めておかないと、後から棚卸しや整理が必要になる。

## Decision

RBACは、最小権限とスコープ分離を基本とする。

初期版では、以下の方針とする。

- 個人ではなくグループ単位で付与する
- Subscription全体への付与は最小限にする
- 通常運用はResource Group単位を基本にする
- 確認用途にはReaderを使う
- 一時的な権限は理由と期限を残す

BicepではRBAC Assignmentをモジュール化する。ただし、公開リポジトリには実環境のPrincipal IDを含めない。

## Alternatives Considered

| 案 | 判断 |
|---|---|
| Subscription全体でまとめて権限付与する | 管理範囲が広すぎるため不採用 |
| Resource単位まで細かく分ける | 初期版では管理負荷が高いため不採用 |
| Resource Group単位を基本にする | 運用しやすさと責任範囲のバランスがよい |

## Consequences

権限範囲を分けることで、作業者の操作範囲と責任範囲が追いやすくなる。

一方で、グループ管理と棚卸しの運用が必要になる。
