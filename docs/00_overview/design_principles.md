# Design Principles

## 1. 基本方針

このリポジトリでは、中堅規模の組織がAzure利用を広げる前に、最低限整えておきたいガバナンスと運用標準を整理する。

大規模なEnterprise Scale Landing Zoneをそのまま再現するのではなく、まずは小さく始められる範囲に絞る。対象は、Subscription配下でのリソース管理、Policy、RBAC、Tag、Log、Cost、例外運用、Evidenceの管理である。

この構成の目的は、Azureリソースを作ること自体ではない。リソースの作成後に、誰が管理するのか、どのルールで運用するのか、例外をどう扱うのか、変更結果をどう確認するのかを明確にすることを重視する。

## 2. Lightweight Landing Zoneとして扱う理由

本構成では、フルスケールのLanding Zoneではなく、Lightweight Landing Zoneとして扱う。

理由は、初期段階からすべての設計領域を作り込みすぎると、検証コストや運用負荷が大きくなり、実際の導入判断が難しくなるためである。

まずは、以下のような最低限の統制から始める。

- リソースの配置先を明確にする
- 権限付与の単位を決める
- 必須タグを定義する
- ログの出力先を標準化する
- コスト管理に必要な情報を残す
- Policyで逸脱を検出する
- 例外時の扱いを決める
- 実行結果をEvidenceとして残す

この範囲であれば、個人検証環境でも再現しやすく、実務の設計検討にも転用しやすい。

## 3. Governanceを主軸にする理由

Azure環境は、リソースを作るだけであれば比較的早く始められる。一方で、利用が広がると、権限の過剰付与、タグの未設定、ログ未収集、コストの所在不明、例外運用の属人化が起きやすい。

そのため、本リポジトリではネットワークや個別ワークロードの詳細設計よりも、Governance / Policy Baselineを主軸にする。

特に、次の観点を重視する。

- ルールを先に決める
- ルールをIaCで再現できるようにする
- 例外を曖昧に扱わない
- 実行結果をEvidenceとして残す
- 運用担当者が後から追える形にする

この考え方により、Azure利用が増えた場合でも、管理が個人依存になりにくい状態を目指す。

## 4. Audit First / Deny Later

Policyは、最初からすべてDenyで止めるのではなく、まずAuditを中心に設計する。

初期段階では、どの程度ルール違反があるか、既存運用とどこが衝突するか、例外がどのくらい発生するかを確認する必要がある。

そのため、最初はAuditで検出し、影響範囲を確認したうえで、必要なものからDenyへ移行する方針とする。

例外的に、明確に避けるべき設定についてはDenyを検討する。ただし、その場合も、事前に影響範囲と例外申請の流れを決めておく。

## 5. RBAC設計の考え方

RBACは、最小権限とスコープ分離を前提にする。

便利だからという理由で、Subscription全体にOwnerやContributorを広く付与しない。運用上必要な権限を確認し、可能な限りResource Group単位、または用途別のグループ単位で付与する。

設計時には、以下を確認する。

- 誰が作業するのか
- どの範囲で作業するのか
- どの操作が必要なのか
- 恒久権限なのか、一時的な権限なのか
- レビューや棚卸しができる形になっているか

RBACは一度付与すると放置されやすいため、付与時点だけでなく、棚卸しや削除の運用も考慮する。

## 6. Tag / Log / Costを運用標準として扱う

Tag、Log、Costは、後から整理しようとすると手戻りが大きい。

特にタグは、コスト配賦、所有者確認、環境区分、運用問い合わせの起点になる。必須タグがない状態でリソースが増えると、あとから整理する負荷が高くなる。

ログについても、障害発生後にDiagnostic Settingsが未設定だったことに気付いても、過去の情報は取得できない。

そのため、本構成では、Tag / Diagnostic Settings / Log Analytics / Cost管理を、後付けの運用作業ではなく、初期設計の一部として扱う。

## 7. Evidenceを残す理由

作業を実施しただけでは、後から内容を確認できない。

特に、Policy割り当て、RBAC設定、Diagnostic Settings、デプロイ結果、What-If結果は、実行した事実と結果を残しておく必要がある。

Evidenceは、単なるスクリーンショット置き場ではなく、次の確認に使う。

- 何を変更したか
- 変更前に何を確認したか
- 実行結果はどうだったか
- 想定外の差分はなかったか
- 後続作業に影響がないか

本リポジトリでは、Evidenceを設計・実装・運用のつなぎとして扱う。

## 8. AVD運用標準化の位置づけ

AVD関連の資料とスクリプトは、本リポジトリのサブテーマとして扱う。

主目的はAVD環境そのものの設計ではなく、実運用で発生しやすい作業を、確認、実行、記録まで含めて標準化することである。

例えば、セッションホストの削除、Personal Desktopのユーザー割当、HostPoolの棚卸しなどは、手順や確認観点が曖昧なまま作業すると、利用者影響や削除漏れが発生しやすい。

そのため、AVD運用標準化では、次の観点を重視する。

- 対象を入力ファイルで明確にする
- 実行前に状態を確認する
- DryRunまたはWhatIfを用意する
- Active sessionなど利用者影響を確認する
- スキップ理由を記録する
- 実行結果をCSVやログで残す

これは、Azure Governanceの考え方を実運用へ適用した例として位置づける。

## 9. 低コスト検証と削除可能性

本構成は、個人検証環境でも扱えるように、低コストで確認できる範囲を優先する。

長期間稼働するリソースや高額になりやすい構成は、初期段階では避ける。検証後に削除できることも設計条件に含める。

そのため、Runbookにはデプロイ手順だけでなく、検証後の削除手順も含める。

## 10. 今後の拡張方針

初期版では、Governance / Policy Baselineを中心に作成する。

将来的には、以下の領域を追加検討する。

- Hub-Spokeネットワーク
- Private Endpoint設計
- Key Vaultの標準化
- Microsoft Defender for Cloudの基本設定
- Azure Monitor Alert設計
- GitHub ActionsによるBicep検証
- Policy as Codeの拡張

ただし、初期版では範囲を広げすぎず、まずはGovernance Baselineとして読みやすく、再現しやすい状態を優先する。
