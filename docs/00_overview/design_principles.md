# Design Principles

## 1. 基本方針

このリポジトリでは、Azure利用を広げる前に整えておきたい、最小限のガバナンスと運用標準を整理します。

大規模なLanding Zoneを最初から作り込むのではなく、Subscription単位で検証しやすい範囲から始めます。対象は、Policy、RBAC、Tag、Log、Cost、例外運用、Evidenceです。

## 2. 小さく始める

初期版では、必要な統制をすべて盛り込むのではなく、運用に乗せやすい範囲に絞ります。

最初に整える対象は以下です。

- Resource Groupの用途を分ける
- 権限付与の単位を決める
- 必須Tagを定義する
- ログ出力先を決める
- Policyで逸脱を検出する
- 例外の扱いを決める
- 確認結果をEvidenceとして残す

この範囲であれば、個人検証環境でも再現しやすく、後からManagement Groupや複数Subscription構成へ拡張しやすくなります。

## 3. Governanceを主軸にする

Azureは、リソースを作るだけなら比較的早く始められます。一方で、利用が広がると、権限の過剰付与、Tag未設定、ログ未収集、コストの所在不明、例外運用の属人化が起きやすくなります。

そのため、本リポジトリでは、個別ワークロードよりもAzure Governance / Policy Baselineを主軸にします。

重視する観点は以下です。

- ルールを先に決める
- ルールをIaCで再現できるようにする
- 例外を曖昧に扱わない
- 実行結果を記録する
- 運用担当者が後から追える形にする

## 4. Audit First / Deny Later

Policyは、まずAudit中心で設計します。

初期段階では、既存運用との衝突や例外の発生状況を確認する必要があります。そのため、最初からDenyで止めるのではなく、Auditで見える化し、影響を確認してからDenyへ移行します。

明確に禁止すべき設定をDenyにする場合も、事前に影響範囲と例外申請の流れを決めます。

## 5. RBACは最小権限とスコープ分離を基本にする

RBACは、作業者に権限を渡すためだけの設定ではありません。

誰が、どの範囲で、どの操作を行えるのかを明確にするための設計要素です。

設計時には以下を確認します。

- 作業者または作業グループ
- 作業対象のスコープ
- 必要な操作
- 恒久権限か一時権限か
- 棚卸しや削除ができるか

Subscription全体へのOwnerやContributor付与は最小限にします。

## 6. Tag / Log / Costは初期設計に含める

Tag、Log、Costは、後から整理しようとすると手戻りが大きくなります。

Tagは、所有者、環境、用途、コストの確認に使います。Logは、障害対応や監査対応の前提になります。Costは、不要リソースの発見や費用説明に関わります。

そのため、これらは後付けの運用作業ではなく、初期設計の一部として扱います。

## 7. Evidenceを残す

作業を実施しても、結果が残っていなければ後から確認できません。

Evidenceでは、以下を記録します。

- 何を確認したか
- どのコマンドまたはRunbookを使ったか
- 結果はどうだったか
- 未確認項目は何か
- 次の対応が必要か

Evidenceは、スクリーンショット置き場ではなく、設計、実装、運用確認をつなぐ記録として扱います。

## 8. AVD運用標準化はサブテーマとして扱う

AVD関連の資料とスクリプトは、Azure Governanceの考え方を実運用へ適用した例です。

対象は、HostPool棚卸し、SessionHost整理、Personal Desktop割当、接続不可時の切り分けなどです。

重視する観点は以下です。

- 対象を入力ファイルで明確にする
- 実行前に状態を確認する
- DryRunを用意する
- Active sessionなど利用者影響を確認する
- スキップ理由を記録する
- 実行結果をCSVやログで残す

## 9. 低コストで検証し、削除できる構成にする

個人検証環境でも扱えるように、初期版では低コストで確認できる構成を優先します。

また、検証後に不要リソースを削除できることも設計条件に含めます。作成手順だけでなく、Teardown手順もRunbookに含めます。

## 10. 今後の拡張方針

初期版では、Azure Governance / Policy Baselineを中心にします。

将来的には、以下を追加検討します。

- Management Groupへの展開
- Hub-Spokeネットワーク
- Private Endpoint設計
- Key Vault標準化
- Microsoft Defender for Cloud基本設定
- Azure Monitor Alert設計
- GitHub ActionsによるBicep検証
- Policy as Codeの拡張

ただし、まずは初期版として読みやすく、再現しやすく、検証できる状態を優先します。
